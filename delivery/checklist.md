# $49 fix: delivery checklist

Scope: 1 Supabase project, up to about 15 tables, delivered in 48 hours.
Time: the tools run in minutes. The real work is the seed file and reading functions in step 4b: plan 1 to 2 hours. Anything bigger gets a quote first.
Work only on a local copy. Never connect to the client's live database.

## 0. Before you start
- [ ] The client said "I agree" to `permission.md` (keep the message).
- [ ] You have the repo (GitHub read access or a zip).
- [ ] The repo has `supabase/migrations/`. If not, ask the client to run
      `supabase db dump --schema-only -f schema.sql` and send you the file. No data.

## 1. Agent blast-radius scan (the repo)
```
mkdir -p out
karchi-guard scan CLIENT_REPO --json > out/scan.json
```

## 2. Local copy of the database (schema only)
```
cd CLIENT_REPO
supabase start -x realtime,imgproxy,mailpit,postgres-meta,studio,edge-runtime,logflare,vector,supavisor
```
With a schema dump instead of migrations: copy it to `supabase/migrations/00000000000000_schema.sql` first.
If port 54322 is busy (another local Supabase is running), run `supabase stop` there, or change the ports in this copy's
`supabase/config.toml` and use the new db port in step 4.

## 3. Supabase Security Advisor (on the local copy)
```
supabase db advisors --local --type security --output-format json > ../out/advisors.json
```

## 4. rlsgrid: can user A reach user B's rows? (local copy only, it writes test rows)
```
export DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
rlsgrid init --from-db --out ../out/rlsgrid.toml
```
Edit `../out/rlsgrid.toml` before running (see `dev/rlsgrid.toml`):
- If rows belong to `auth.users` (most Supabase apps): add `"auth"` to `schema_search_path` and remove it from `[exclude] schemas`.
  Without this, every test insert fails its foreign key and rlsgrid tests nothing.
- If seeding fails with `428C9` (`generated always as identity`): on the local copy only, run
  `alter table T alter column id set generated by default;` for each listed table.
```
rlsgrid check --config ../out/rlsgrid.toml --json > ../out/rls.json
```
Exit 1 means leaks were found. If the report says "could not run on most tables", fix the setup and run again.
Use `check` (it cleans up). Plain `seed` leaves rows behind unless you pass `--state-out` and run `teardown --state`.

## 4b. When rlsgrid skips most probes (most real apps): two-tenant test by hand
Real schemas have CHECK and NOT NULL rules that rlsgrid's random data breaks (Kalvio Desk: 225 of 300 probes
skipped, and it still printed "Safe"). Then:
1. Write a small seed file for the local copy: two tenants, one user each in `auth.users`, the link row
   (for example `members`), and one valid row in every table for each tenant. Example: Kalvio Desk practice run.
2. Run the test as user A. It runs in a rolled-back transaction:
```
psql "$DATABASE_URL" -v user_a=<uuid> -v tenant_a=<uuid> -v tenant_col=clinic_id -f delivery/two-tenant-test.sql
```
   `own_rows` must be above 0 in every table (otherwise the test user is not set up and the test means nothing).
   `other_tenant_rows` must be 0.
3. Read the code of every SECURITY DEFINER function that anon can call. For each one that logged-in users can call
   with an id, call it as user A with tenant B's ids inside `begin; ... rollback;`. It must fail or do nothing.
   Then call it with tenant A's own ids. It must work (control).
4. Write the results as a short Markdown table in `out/two-tenant.md`.

## 5. Report
```
karchi-guard report --scan out/scan.json --advisors out/advisors.json --rlsgrid out/rls.json \
  --project "CLIENT APP" --out out/report.md
```
If you used step 4b, add `--two-tenant out/two-tenant.md` and leave out `--rlsgrid` when its run was not trustworthy.
Read the whole report. Delete anything that is not true for this app. Check that it shows names only.

## 6. Fix
- [ ] New branch `fix/supabase-safety`.
- [ ] One migration in `supabase/migrations/` with the RLS and function fixes from the report.
      Check that every policy uses the right owner column. Do not guess.
- [ ] MCP config and `.claude/settings.json` fixes, if the scan found any.
- [ ] Keys found by B1/B2: tell the client to rotate them. You never touch their dashboard.
- [ ] `supabase db reset` on the local copy, then repeat steps 1, 3 and 4. Save the new report as `out/report-after.md`.
- [ ] Open the pull request. Paste the before and after counts into the description.

## 7. Hand over and clean up
- [ ] Send `report.md`, `report-after.md` and the PR link.
- [ ] Ask the client to run the Advisor in their dashboard after merging.
- [ ] `supabase stop --no-backup`, then delete the repo copy and `out/` within 7 days.
